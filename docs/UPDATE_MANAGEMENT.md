# LASS 1.3.1 수정 및 업데이트 관리

## 8개 요청에 대한 변경

| 항목 | 확인한 원인 | 반영 방식 |
|---|---|---|
| 1. 노트 복귀 후 폴더 클릭 시 Chatting 전환 | 폴더 선택 이벤트가 대화 모드 진입 함수를 호출 | 폴더 펼침과 화면 모드를 분리하여 현재 노트·패널 상태 유지 |
| 2. `no such table: collections` | 텍스트 검색 전용 DB에 과거 벡터 테이블이 없는데 삭제 실행 | 공통 벡터 삭제 함수에서 테이블 존재 여부 확인. 기존 데이터 삭제·이동 경로에도 적용 |
| 3. PDF와 다른 요약 | 긴 원문 일부만 표본 추출하고 생성된 메모를 반복 요약 | 전체 원문을 순서대로 읽고 AI는 문장 번호만 선택. 실제 표시 문장은 원문에서 가져옴. 형식 오류 시 해당 원문을 표시 |
| 4. 데이터 보존 업데이트 | 기존에는 새 버전 확인·검증·백업 흐름이 없고 제거 시 데이터 삭제 | 앱의 ‘앱 업데이트’에서 공식 릴리스 확인 → 다운로드/해시 검증 → 데이터 백업 → 기존 앱 위에 설치 |
| 5. 관리 방식 | 아래 운영 절차 참고 | 버전당 하나의 정식 GitHub 릴리스와 동일 AppId의 설치 프로그램 사용 |
| 6. 처리 중 텍스트가 하단 출력 | 업로드 버튼이 있는 하단 컨테이너에서 임시 출력 생성 | 상단 전사 컨테이너의 출력 위치를 사용하여 최근 120개 구간 누적 표시 |
| 7–8. 한국어 파일도 언어 오류로 중단 | 한 구간의 자동 언어 태그가 다른 언어면 예외 발생 | 태그만 잘못되고 문자가 한국어·영어이면 계속 처리. 다른 언어 문자가 출력되면 해당 구간 재인식 후 확인 필요 표시. 남은 구간 계속 처리 |

## 왜 이 업데이트 방식을 선택했는가

**기존 Inno Setup 설치 프로그램으로 덮어쓰는 방식**을 사용한다. 이미 존재하는 Windows 설치·제거 등록, 실행 파일 교체, 사용 중인 파일 닫기 기능을 재사용하므로 별도 업데이트 서비스나 자체 파일 교체 엔진이 필요 없다. 앱은 사용자가 업데이트 확인과 설치를 눌렀을 때만 네트워크에 접속하거나 설치 파일을 실행한다.

프로그램은 `%LOCALAPPDATA%\Programs\LASS`, 사용자 데이터와 모델은 `%LOCALAPPDATA%\LASS`에 보관한다. 프로그램 파일과 저장 자료의 수명 주기를 분리하면 업데이트가 DB나 모델을 덮어쓰지 않는다. 같은 AppId를 유지하여 기존 설치 위치와 Windows 앱 등록을 사용한다.

1.3.0에는 사용자 데이터·모델을 삭제하는 `[UninstallDelete]` 규칙이 있었다. 이 규칙을 제거하는 것만으로는 이전 설치의 삭제 로그에 남은 규칙이 사라지지 않으므로 `UninstallLogMode=overwrite`로 삭제 로그도 갱신한다. 일반적으로 Inno Setup은 로그 추가를 권장하지만, 이 경우 과거의 파괴적인 규칙 제거가 필요하다. 매번 `[Files]`에서 전체 앱 파일을 등록한다. 설치 폴더에 남는 이전 버전 전용 파일은 데이터 보호를 위해 일괄 삭제하지 않는다.

업데이트 전에 SQLite backup API로 커밋된 WAL 데이터까지 포함한 DB 스냅샷을 만들고 `integrity_check`를 실행한다. 관리되는 첨부자료와 기타 저장 파일도 복사한다. 로그·재생성 가능한 미리보기는 제외한다. 백업은 `%LOCALAPPDATA%\LASS\backups\날짜-시간`에 저장한다. 외부 경로로 연결한 원본 파일과 모델은 설치에서 건드리지 않으며 백업에 중복 복사하지 않는다. 백업 실패 시 설치를 시작하지 않는다. 백업을 자동 삭제하지 않으므로 관리자가 복구 필요성을 확인한 뒤 정리한다.

다운로드는 HTTPS 공식 저장소의 정식 릴리스만 허용하고 파일 크기와 SHA-256을 검증한다. 중단된 다운로드는 이어받을 수 있다. 검증 실패 시 확정된 설치 파일로 변경하지 않는다. 해시는 전송 손상·잘못된 파일을 확인하는 수단이며 코드 서명의 대체재는 아니다. 배포가 확대되면 Windows 코드 서명 인증서를 적용하고 서명 검증을 추가하는 것이 다음 단계다.

대용량 CUDA 런타임을 포함하므로 지금은 전체 설치 파일을 내려받는다. 차등 업데이트는 다운로드량을 줄일 수 있으나 버전별 패치·복구 경로가 복잡해진다. 현재 단계에서는 전체 설치 프로그램 하나를 검증하는 방식이 관리와 장애 복구에 유리하다.

## 버전과 배포 절차

1. 버전은 `src/__init__.py`와 `pyproject.toml`에서 함께 변경한다. 빌드 스크립트는 `src.__version__`을 설치 프로그램에 전달한다. 설치 스크립트의 기본 버전도 함께 유지한다.
2. 회귀 테스트를 실행하고 `scripts/build_desktop.py --iscc <ISCC.exe>`로 번들·설치 프로그램을 만든다. `--skip-bundle`도 현재 소스와 번들의 해시 일치를 검사하여 오래된 번들의 오배포를 막는다.
3. `v1.3.1` 같은 정식 태그의 GitHub Release에 `LASS-Setup-1.3.1.exe`와 자동 생성되는 `LASS-Setup-1.3.1.exe.sha256`을 함께 첨부한다. 두 파일을 준비한 뒤 정식으로 공개한다. 초안·사전 릴리스는 업데이트 대상에서 제외한다.
4. 설치된 앱의 왼쪽 목록에서 **앱 업데이트 → 업데이트 확인 → 백업 후 업데이트 설치**를 사용한다. 요약·마이크 녹음 중에는 업데이트 버튼을 비활성화한다. 설치 창에서 앱 닫기를 진행하고 완료 후 실행한다.
5. DB 변경은 기존 저장 값을 보존하는 추가형 변경을 기본으로 한다. 실패한 릴리스는 공개를 중단하고 수정 버전을 배포한다. 실행 파일을 이전 버전으로 내리는 것만으로 DB 호환성이 보장되지 않으므로 자동 다운그레이드는 제공하지 않는다.

**1.3.0 사용자는 기존 앱을 삭제하지 말고 1.3.1 설치 파일을 직접 실행해 처음 한 번 업데이트해야 한다.** 이전 앱에는 업데이트 메뉴가 없고 이전 제거 프로그램은 데이터를 삭제한다. 첫 전환 전에 `%LOCALAPPDATA%\LASS\data` 폴더를 별도로 복사하면 추가 복구 지점을 확보할 수 있다. 이후에는 앱 내 업데이트가 자동 백업을 만든다.

백업 복구 시 LASS를 완전히 종료한 후 백업의 파일을 원래 `data` 경로에 복원한다. DB만 복원할 경우 첨부자료와의 일관성을 확인한다. 기존 `data`는 별도 이름으로 보관한 상태에서 복구하고, 신규 버전의 DB 변경과 호환되는 앱 버전으로 실행한다.

## 검증 범위와 한계

폴더 복귀 상태, FTS 전용 DB에서의 예전 인덱스 정리, 긴 원문의 모든 구간 소비, 잘못된 문장 번호/모델 생성 수치 차단, STT 태그 오판과 다른 언어 문자 재인식, 상단 전사 출력, 릴리스·해시 검증, WAL 포함 데이터 백업을 회귀 테스트로 확인한다.

실제 EXAONE CUDA 모델로 2페이지의 통제된 PDF를 요약하고 발췌 문장 7개를 추출 원문과 대조했다. 실제 SenseVoice 모델로 23초 영어 음성의 마지막 부분 구간까지 처리했고, 동일 모델 저장소의 고정 리비전에 포함된 공개 한국어 테스트 음성도 `ko`로 인식하여 전사를 완료했다. 한국어 언어 오판은 모의 인식 결과로 검증했으며, 사용자가 문제를 발견한 PDF·한국어 녹음 파일은 제공되지 않아 동일 파일의 재현은 확인하지 못했다. 기존 Windows 설치를 실제로 덮어쓰거나 제거하는 작업은 사용자 환경에서 실행하지 않았다.

발췌 방식은 모델이 새 사실을 만들어내는 문제를 차단하지만 OCR/STT 자체의 오인식이나 문장 선택에 따른 맥락 누락까지 없애지는 않는다. 기존에 저장한 요약을 자동으로 바꾸지 않으므로 문제가 있는 노트는 업데이트 후 **다시 요약하기**로 새 방식을 적용한다.
